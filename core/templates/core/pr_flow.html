The Pull Request, step by step.

A pull request (PR, or "merge request" on GitLab) asks the team: "I made these changes on my branch; please review them and pull them into the main codebase." The proposal shows the exact diff, runs automated checks, collects reviewer comments, and records the decision. Nothing reaches main until the team agrees it should.

A proposal

A branch plus a description of what changed and why. It's a request for a decision, not a finished fact.

A conversation

Reviewers comment on specific lines, ask questions and suggest fixes. The author pushes more commits in reply.

A gate

Branch protection can require passing CI and approvals before the merge button unlocks.

      Who talks to whom (sequence)
      
        
      

      sequenceDiagram
    actor A as Author
    participant G as GitHub
    participant CI as CI runner
    actor R as Reviewer
    A->>G: git push feature branch
    A->>G: open pull request
    G->>CI: trigger checks
    G->>R: request review
    CI-->>G: tests + lint result
    R->>G: line comments
    alt changes requested
        G-->>A: notify
        A->>G: push fix commits
        G->>CI: re-run checks
        R->>G: approve
    else approved
        R->>G: approve
    end
    A->>G: merge (checks green + approved)
    G->>G: main updated, branch deleted

      
        
      

        
      Lifecycle of a PR (state)
      
        
      

      stateDiagram-v2
    [*] --> Draft : opened as draft
    [*] --> Open : opened
    Draft --> Open : ready for review
    Open --> ChangesRequested : reviewer requests changes
    ChangesRequested --> Open : author pushes fixes
    Open --> Approved : reviewer approves
    Approved --> Open : new commits pushed
    Approved --> Merged : checks pass and merge
    Open --> Closed : abandoned
    Closed --> Open : reopened
    Merged --> [*]

      
        
      

        
      Decision flow before merge
      
        
      

      flowchart TD
    A([PR opened]) --> B{CI green?}
    B -- no --> F["Author fixes and pushes"] --> B
    B -- yes --> C{Reviewer approves?}
    C -- "changes requested" --> F
    C -- yes --> D{Conflicts with main?}
    D -- yes --> E["Rebase or merge main into branch"] --> B
    D -- no --> M([Merge into main])
    M --> X["Deploy pipeline / delete branch"]

      
        
      
    
      

    
    
      
        
      Merge strategies
      
        
      The same PR can land in three ways. Pick a tab to compare the resulting history.
      
        
      
            
            
            
        
      
        
      
            
      
                
      Merge commit keeps every commit and adds a merge commit that ties the branch in. History is complete but can look busy.
      
                
      

      gitGraph
    commit id: "A"
    branch feature
    commit id: "f1"
    commit id: "f2"
    checkout main
    commit id: "B"
    merge feature id: "Merge PR"

      
                
      
            
      
            
      
                
      Squash combines all branch commits into one commit on main. History stays clean with one commit per PR. This is the most common choice for feature work.
      
                
      

      gitGraph
    commit id: "A"
    commit id: "B"
    commit id: "feat: f1+f2 (#42)"

      
                
      
            
      
            
      
                
      Rebase replays each branch commit on top of main. History is linear and keeps individual commits, but those commits get new hashes.
      
                
      

      gitGraph
    commit id: "A"
    commit id: "B"
    commit id: "f1'"
    commit id: "f2'"
